<objective>
Land the breaking `SkillRegistry` port change and the skill-observability emission in `AgentLoop`: every skill-activation pass produces a `kore.skill.activate` OTel span with name/count/duration attributes (OBSV-03), and when >=1 skill matches, an `AgentEvent.SkillActivated` is emitted on the bus (OBSV-04). The new return type (`List<ActivatedSkill>`) ripples through both in-repo implementations and the loop in one cohesive change so the codebase stays compilable at every step.

Purpose: Make skill activation observable from both the trace (always, even count=0 — answers "why didn't my skill activate?") and the event bus (only on >=1 match — keeps broker traffic lean). This is the foundation the observer reactions (Plan 05-03) and the KoreTracer attr branch (Plan 05-04) build on.
Output: `ActivatedSkill` data class, `AgentEvent.SkillActivated` subclass, the instrumented `AgentLoop` span+event, the migrated `SkillRegistryAdapter`, and extended tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AgentLoop → event bus (Kafka/RabbitMQ in opt-in topologies) | `AgentEvent.SkillActivated` crosses the bus and may reach a remote broker. Its payload is the security-relevant surface. |
| AgentLoop → OTel backend | Span attributes (`kore.skill.names`) are exported to any configured OTel backend. |

This phase adds NO new external inputs, network endpoints, auth, or persistence. Skill names originate from in-repo YAML (trusted), not user input.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-03 | Information Disclosure | `AgentEvent.SkillActivated` payload on the message broker | mitigate | Prompts are DELIBERATELY excluded from the event (D-06) — they can be KBs and may contain sensitive content unsuitable for broker transport. Only `agentId`, `skillNames` (low-sensitivity identifiers), and `durationMs` cross the bus. Enforced by the `data class` field set; the serialization round-trip test guards against accidental field addition. |
| T-05-04 | Information Disclosure | `kore.skill.names` span attribute exported to OTel backend | accept | Skill names are non-PII identifiers from in-repo YAML (mirrors Phase-2 D-24 "configured names, no PII in tag values"). Low risk; documented, not mitigated further. |
| T-05-SC | Tampering | npm/pip/cargo installs | n/a | This plan installs NO packages (no dependency changes — OTel + serialization already on the classpath). No package-legitimacy checkpoint required. |
</threat_model>
